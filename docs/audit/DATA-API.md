# Data model, operations and service contracts

This is a proposed implementation specification inferred from the visible application. No tables or endpoints below exist yet. Keep normal APIs in the Next.js application on Vercel. Use one relational PostgreSQL database initially; choose a provider/region with an appropriate free or smallest paid tier and measured connection/backup needs. Object storage holds binaries. Avoid separate microservices per ERP module.

## Schema conventions and trust boundaries

Use UUID primary keys; all business rows carry `tenant_id`, scoped rows `company_id`, timestamps, creator/updater and optimistic `version`. Compound foreign keys must keep tenant/company boundaries intact; never accept a tenant ID from the client as authorization. Query tenant context comes from verified session membership. Use database constraints plus application authorization; PostgreSQL RLS can be defense-in-depth only when connection pooling and tenant context are correctly tested. Define unique constraints including tenant, not accidental global uniqueness for user-facing codes.

Money uses fixed decimal or integer minor units with explicit ISO currency and rounding policy; quantity/rate precision is separate. Dates without times remain SQL dates; event times are UTC timestamptz, schedules store IANA timezone and local wall-clock recurrence. Do not parse display strings as identifiers or next-run timestamps. Configurable fields use versioned typed schemas; JSONB is suitable for validated extension values, not for replacing core relationships with arbitrary `Record<string,string>`.

Store audit events append-only: actor identity/type, membership/role snapshot, tenant/company, action, entity ID/version, request/correlation ID, before/after redacted differences, outcome, timestamp. Derive IP from trusted deployment headers only and redact personal data appropriately. Domain mutation, audit and outbox event commit atomically. Logs must not store full prompts, credentials, payroll data or government IDs by default.

## API contract

All endpoints return `{data, meta?: {cursor, total, requestId}}` or `{error: {code, message, fields?, requestId, retryable}}`. Suggested statuses: 400 malformed, 401 unauthenticated, 403 forbidden, 404 scoped missing, 409 stale/invalid transition/idempotency conflict, 422 field/business validation, 429 limited, 502/503 provider unavailable. Avoid entity-existence leakage across tenants. Cursor pagination with stable sort and bounded page size, allowlisted filters; exports use the same predicates and authorization.

For write actions use validated DTOs with unknown keys rejected, CSRF/origin protection for cookie sessions, `Idempotency-Key` for financial/job/external side effects, and expected version for mutable records. Retry same key/body returns same result; same key/different body conflicts. Mutation responses include new version. OpenAPI + runtime validators + generated client must stay aligned. Server Actions may wrap the same services; do not implement divergent authorization in two paths.

## Background state machine and recovery

Persist job before acknowledging API request. Transactionally reserve credits/create outbox; dispatcher publishes/claims with stable operation key. States: queued→running→waiting_for_review or waiting_for_provider→running→succeeded/failed/cancelled. Track attempt number, lease expiry, worker token/fencing version, checkpoint, progress, error category, retry time, provider request ID and artifact IDs. Retries use exponential backoff with jitter and finite attempts; dead letters visible/replayable by authorized operator. Worker crashes before/after external call must reconcile provider idempotency rather than blindly repeating a payment/email/posting.

A scheduler computes occurrences from timezone-aware recurrence, inserts unique `(schedule_id, scheduled_for)` and advances `next_due_at` transactionally. Run-now has its own key. Decide overlap (`skip`, queue or cancel previous), missed-run bounded catch-up and DST duplicate/gap policy before acceptance. Pause affects new occurrences; in-flight cancellation is separate. No per-tenant redeploy to change cron. Business due work (SLA, recurring invoices, retention) uses the same scheduler/job infrastructure, never browser timers.

## Required tests

At minimum two tenants, two companies, admin/member/manager/employee/external/runner identities. Test reads, mutations, exports, search and signed downloads against cross-tenant/company/party access. Parallel requests must not double-spend credits, approve twice, reimburse twice, duplicate subscription invoices, oversell reserved stock, reuse invite/recovery tokens or create duplicate occurrence jobs. Verify webhook replay, out-of-order events, stale versions, provider timeout after success, lost worker lease, cancelled job late callback and exhausted retries. These are business correctness tests, not implementation-mirroring unit tests.
