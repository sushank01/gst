# UI-to-backend requirements matrix

Status vocabulary: **V** = verified in source/UI as a visible requirement; **I** = implementation inference necessary to make it real; **D** = product/provider decision. All API routes below are proposed contracts, not existing endpoints. Base `/api/v1`; business routes authenticate and scope by tenant, company and resource permissions. The file inventory contains exact field definitions and event handlers; these tables add semantics and acceptance requirements.

Every row inherits: meaningful loading/skeleton, first-use empty, filtered-empty, field/server validation, retryable network failure, permission denied, expired session, stale-update conflict, unavailable provider, disabled entitlement and success confirmation. Lists need stable sort, URL-backed filters and pagination; mutations need pending/duplicate-submit protection and cache refresh. Details need refresh/deep-link/back behavior. Downloads need authorized expiring URLs and actual matching MIME/file content. Never use empty state to hide a fetch failure.

## Exhaustive sub-surface expansion

The matrix is a semantic layer, not permission to omit data-driven pages. Expand these source registries into one coverage row per entry AND per nested tab/action:

- `hrData.hrGroups` (people/time/development/care/admin) and `hrSettings`, all `HrPage.modal`, `HrSubTab.modal`, `entries` fields and selectors.
- `crmData.crmTabs`, `settingsGroups` (Pipeline & Data, People & Work, Inbound, Outbound, Channels, Automation, Branding), pipeline stages and all `crmModals`.
- `travelExpenseData.teTabs`, settings nav and segment/custom fields; `assetData.assetTabs`, settings/master taxonomy groups; `supportData.supportNav`, report tabs, settings nav, statuses/priorities/channels and gated sections; `posData.posNav`, report/settings tabs and document kind/status sets.
- `pitchData.pitchNav`, schemas/categories/brand fields; `businessData.suiteCategories` every tool slug, featured/quick access; `agentCatalog.agentGroups` every agent; `appData.apps`, webApps/mobileApps and vibeSkills; `vibeData.capabilities`, controls and nav; `agentStudioData.studioGroups` and template categories.
- `portalData.portalTabs` and each maskable field; connectorData's 27 connector entries; complianceData inventory/flows; lib/pages product/info/vibeSkills for all public slugs.

For each generated interaction ID in the source ledger assign R-ID, actual route+query+tab, role, entity, API, side effect, validation, all state variants, test ID and artifact evidence. If an interaction is rendered by a map, append the data item's stable ID to the call-site ID. The line number is provenance, not a durable product identifier; retain old→new mapping after refactors.

## Decisions that actually need product input

1. **D1 execution**: is this AWS account already eligible for App Runner? If 5–10-minute uncheckpointable jobs are required, approve an appropriate AWS job runner or another durable service. No silent purchase/substitution with a paid Vercel workflow product.
2. **D2 release catalog**: deliver all visible enterprise apps, gated web/mobile and generation capabilities, or explicitly choose a first release subset and remove/label promises accordingly. Incomplete gated features cannot be represented as shipped by an upgrade button.
3. **D3 credentials/provider contracts**: chosen model/media/OCR/email/payment providers, OAuth app registrations, licensed banking/KYC/credit/health/logistics/SAP access. Implement adapters and test contracts independently; live credentials block only live integration verification.
4. **D4 commercial/jurisdiction**: legal operator/brand, approved plan prices/credit economics, currencies, operating country and tax/payroll/compliance requirements, residency/retention, recovery objectives. Do not treat copied Apragya prices or GST slabs as approved policy.
5. **D5 external audiences**: employee identity source, partner portal domain/invitation rules, public knowledge/widget access, mobile delivery offline expectations. Use conservative scoped access until clarified.

Routine choices (TypeScript organization, shared UI structure, SQL migration conventions, test layout, API envelope) should be resolved by the implementing agent. Do not stop all work waiting for D1–D5; isolate the dependent loops and advance the rest.
