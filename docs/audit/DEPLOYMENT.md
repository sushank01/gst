# Architecture, execution, environment and deployment decisions

Verified against official documentation on 2026-09-21. Recheck limits, availability, eligibility, pricing and region before provisioning. These are specifications; nothing was provisioned, purchased or deployed in this audit.

## Decision and user preference

Keep the frontend, authentication, domain services and ordinary request/response APIs in **one Next.js application on Vercel**. A database/object store are persistence dependencies, not reasons to create a second API server. The source does require real scheduling: hourly admin automations, SLA/escalation, recurring invoices, receipt/inbound processing, scheduled reports and retention. RFP extraction/deck rendering, RAG ingestion, generated builds and RPA are candidates for long work; their real duration is **unknown until implemented and measured**. A 900ms demo delay is not a workload benchmark.

Respect the user's preference to place only genuinely long/background execution on AWS App Runner if feasible. Do not move normal APIs to AWS. Do not silently replace that preference with a paid Vercel workflow product. D1 is a targeted decision gate: App Runner account eligibility, task duration/checkpointability and an approved alternative if necessary. Database schema, durable job contracts, frontend integration and local worker tests can proceed before this choice.

## Deployment paths — choose, do not silently substitute

**A. Vercel-only execution where bounded:** request creates DB job/outbox then returns job ID; an approved scheduler dispatches due tasks to bounded Vercel handlers. Persist checkpoints/retries/lease ownership and status. Authenticated browser polls or SSE reads status; browser closing does not own execution. Use Vercel Cron only on a plan that meets cadence/commercial needs. A third-party paid durable queue/workflow is a product/cost decision, not an assumed dependency. At low volume a DB job table and bounded authenticated dispatcher may suffice, provided retry delivery and stuck-job reaper are explicitly implemented and tested; do not use `after()` alone as durable delivery.

**B. Existing eligible App Runner account, checkpointable work:** Next.js still owns all ordinary APIs. EventBridge Scheduler can enqueue into SQS; SQS and a DLQ provide delivery buffering. A small dispatch adapter can consume messages and call an authenticated App Runner endpoint, awaiting a bounded step (target ≤90 seconds including network margin). App Runner returns a checkpoint/result before the 120s limit. Persist the next step before acknowledging the queue message; retries/dedup/fencing live in DB. Configure queue visibility above worst-case step+dispatch, limit concurrency to measured container capacity, handle visibility extension and failed acknowledgments. Do not imply SQS automatically pushes HTTP to App Runner or App Runner schedules/polls safely in the background. Scheduler→SQS and a queue-to-HTTP dispatcher are additional components/costs, justified only for selected workloads. [Scheduler SQS target](https://docs.aws.amazon.com/scheduler/latest/UserGuide/managing-targets-templated.html).

**C. New AWS customer or truly uninterruptible 5–10-minute task:** App Runner is not a suitable promised solution. Ask D1 to approve an alternative AWS execution mechanism, for example on-demand ECS/Fargate tasks started through scheduler/dispatcher, while keeping Next.js on Vercel. This avoids pretending a web container is a durable job runner. AWS recommends ECS Express Mode for web-service migration, but it provisions load balancing/networking and is not automatically the cheapest batch-worker design. A selected batch-task approach can avoid an always-on ALB; account for image pulls, task startup, public IP/NAT/egress and logs. Start from a measured 0.25vCPU/0.5GB Fargate candidate for light tasks, increasing only from evidence; do not commit to it for headless rendering. [Fargate CPU/memory combinations](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-cpu-memory-error.html).

The durable database model in DATA-API.md is common to all paths. When D1 is unresolved, mark production execution BLOCKED with the exact pending choice and keep implementation progress on independent loops. Do not mark full application complete.

## Cost plan

Assumptions for the initial sizing worksheet: one small tenant, ≤10 concurrent interactive users, ≤100 background jobs/day, mostly provider/network waits, median step <30s, no persistent headless browser, modest file retention. These are planning assumptions, not measured usage. Re-estimate from actual tenant/workload targets and p95/peak RAM, duration and queue age.

For eligible App Runner at 0.25vCPU/0.5GB, one provisioned instance and 730h/month, the documented US-East example rates of $0.007/GB-hour and $0.064/vCPU-hour imply about $2.56/month provisioned memory. CPU for 10 active hours adds approximately $0.16, before minimum billing, extra instances, build/deployment, storage, queue/scheduler, DB, logs, network and taxes. A continuously active equivalent adds about $11.68 CPU/month. These are arithmetic examples, not total application quotes; region matters. App Runner keeps provisioned capacity/memory billed while idle; pausing is not automatic scale-to-zero and makes the service unavailable. [Pricing](https://aws.amazon.com/apprunner/pricing/).

Vercel paid seats/plan base, invocation/CPU/memory/egress, database backups/connections, storage downloads, email, AI tokens/images/OCR and any durable orchestration can dominate this tiny container estimate. Hobby is for personal non-commercial use; verify eligibility before treating free hosting as a commercial deployment plan. [Hobby plan](https://vercel.com/docs/plans/hobby). Record current rate links and a formula per resource, budgets and alerts; do not promise a fixed total without workload/provider/region decisions. Cap worker concurrency/max instances and model spend; pause optional ingestion before breaking core CRUD. Single small instance trades availability/throughput for cost; describe cold starts, DB sleep and restore time honestly.

## Environment contract

The current frontend needs **zero** environment variables. `.env.example` proposes names for confirmed future capabilities, explicitly conditional where the provider/executor is undecided. It is a specification, not a claim consumers exist. No real `.env` was created, overwritten or printed. `.gitignore` now excludes `.env` and `.env.*`, allowing only `.env.example`.

| Variables | Consumer / requirement | Scope and validation |
|---|---|---|
| APP_URL | Auth redirect, links, webhook origin | Server; canonical HTTPS in production; local HTTP permitted only development. |
| DATABASE_URL | ORM/query services | Server only; PostgreSQL URL/TLS, connection pooling appropriate to serverless, separate preview DB. |
| AUTH_SECRET | Chosen session/auth adapter | Server; cryptographically random sufficient entropy; document rotation/session invalidation; final library-specific mapping required. |
| CREDENTIAL_ENCRYPTION_KEY | Encrypt tenant connector tokens in database | Server only; 32 random bytes encoded consistently; versioned encryption format/key rotation, never browser storage. This is not a secrets-manager dependency. |
| SMTP_HOST/PORT/USER/PASSWORD/FROM | Verification, recovery, invites, notifications | Server; TLS mode/port validated; authorized sender domain; local SMTP sandbox in tests. |
| GOOGLE_CLIENT_ID/SECRET | Google sign-in/integrations if enabled | Server; per-environment exact callback allowlist/scopes; no pretend OAuth enabled with blank credentials. |
| MICROSOFT_CLIENT_ID/SECRET/TENANT_ID | Microsoft OAuth if enabled | Server; actual tenant/multitenant configuration recorded; consent/admin scopes explicit. |
| AI_PROVIDER/API_KEY/TEXT_MODEL/EMBEDDING_MODEL | Selected inference and retrieval adapters | Server; provider enum/model registry; blank unsupported provider disables affected capabilities with reason. Add media/OCR variables when selected. |
| OBJECT_STORAGE_REGION/BUCKET/ENDPOINT/ACCESS_KEY_ID/SECRET_ACCESS_KEY | S3-compatible upload/download storage | Server; endpoint allowlist; AWS task role instead of long-lived keys where available. Empty endpoint means AWS native only if implemented. |
| CRON_SECRET | Vercel cron endpoint if selected | Server; random secret validated against Authorization; cron configuration and current plan must match. |
| WORKER_BASE_URL/SIGNING_SECRET | Remote bounded-step worker if approved | Server; HTTPS trusted endpoint; timestamp+body+nonce signature/replay window/key rotation. |
| AWS_REGION/JOBS_QUEUE_URL/JOBS_DLQ_URL | AWS scheduler/queue adapter if approved | Server/worker; account/region matching; IAM role identity; no static AWS account keys required by this template. |
| BILLING_PROVIDER/API_KEY/WEBHOOK_SECRET | Commercial subscription adapter if approved | Server; sandbox/live isolation; webhook raw-body signatures; price mapping validated against provider. |
| ERROR_REPORTING_DSN | Optional error reporting | Server; scrub sensitive payloads. Add public browser DSN separately only if specifically safe/needed. |

All names are server-only; none uses NEXT_PUBLIC. Do not expose encryption/auth/provider credentials in client bundles. Tenant-supplied credentials belong encrypted in DB under the env encryption key, not one env variable per tenant. Do not add speculative credentials for all 27 catalog vendors. When enabling an adapter, document exact keys/scopes/owner/rotation and update example plus startup schema together. Validate required variables conditionally at startup without logging values; disabled optional features must not crash unrelated pages.

## Production `.env` import compatibility

Local Next.js can read an ignored `.env`. Production platforms normally inject configured environment **key/value pairs**, not a user-uploaded `.env` file mounted in the running filesystem.

For Vercel, project Environment Variables lets you set name/value and choose Production/Preview/Development; changes require redeployment. If the current dashboard offers .env import/paste, use it to populate those pairs and review environment scope, but do not rely on it as a file mount. The verified universal path is per-key dashboard entry or CLI `vercel env add NAME production` through stdin (e.g. a securely created temporary file containing **that one value**). `vercel env pull` downloads platform values; it does not upload a dotenv file. For bulk automation implement a dotenv parser and official env API/CLI calls with values passed as structured data/stdin, never `source .env`, `eval`, shell interpolation or command-line secret arguments. [Vercel env management](https://vercel.com/docs/environment-variables/managing-environment-variables), [CLI env](https://vercel.com/docs/cli/env).

For eligible App Runner, set plain-text runtime environment pairs in service configuration/console or `RuntimeEnvironmentVariables` in an image service's API configuration; plain env values are supported independently of Secrets Manager. A source deployment can reference environment configuration in apprunner.yaml, but do not commit real secrets there. A deployment helper may parse the local .env and create a temporary 0600 JSON payload for AWS CLI create/update-service, preserving the existing image/role/network configuration, submit, then remove the temporary file. Do not bake .env into the image, publish it in build context or promise a raw file-upload feature. Restrict service-config IAM readers because environment values remain administratively readable. [App Runner environment management](https://docs.aws.amazon.com/apprunner/latest/dg/env-variable-manage.html), [environment concepts](https://docs.aws.amazon.com/apprunner/latest/dg/env-variable.html). No Secrets Manager or Parameter Store is required by this plan.

## Deployment acceptance runbook

1. Complete D1/D2/D3/D4 and exact env schema; choose approved region adjacent to DB, define preview/prod resource separation and budgets. Confirm auth/email/DNS ownership without publishing copied brand claims.
2. Install from lockfile, real lint/type/unit/integration/browser checks; produce immutable build artifact and migration plan. Inspect client bundles and build logs for secrets.
3. Provision selected DB/storage and minimal executor only as approved. Apply migrations once with a dedicated release role; runtime roles cannot alter schema. Seed taxonomy/configuration only, not fake customer/history/approval data.
4. Configure platform environment pairs, OAuth callbacks, email sender, signed webhooks and scheduler/service IAM. Local .env remains local. Never print env value inventories into reports.
5. Deploy preview, verify server authorization, actual DB persistence across browser/server restart, object access, provider sandbox/live-test endpoints, jobs continuing after browser closes, duplicate delivery/recovery and smallest-instance load.
6. Exercise backup/restore into isolated DB and object/version recovery. Test rollback with backward-compatible migrations, drained/replayable jobs and artifact-version compatibility.
7. Prepare production configuration and publish/deploy only within explicit authorization. This audit explicitly did not deploy. After authorized deployment run scoped smoke/E2E probes, verify real job occurrence and one approved integration, collect logs/metrics without sensitive data and monitor budgets.
8. Claim readiness only with evidence for all accepted requirements; list anything blocked by credentials, product decisions or unavailable execution platform. A green build or working mock screens is insufficient.
