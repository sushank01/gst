# Schema

22 tables across three migrations. `migrations/*.sql` is the source of truth;
this describes the decisions behind it.

## Conventions

| Concern | Rule |
|---|---|
| Identity | `uuid` generated by the database, never by a client |
| Time | `timestamptz` always; bare `date` only for calendar-day facts |
| Money | `numeric(18,4)` **plus an explicit currency column** — never float |
| Tenancy | every business table carries `tenant_id` and cascades from it |
| History | `archived_at`, not `DELETE`, wherever an audit trail must survive |
| Email | stored as entered, compared through a `lower()` unique index |
| Concurrency | `version integer` on anything two people can edit |

## 0001 — identity and tenancy

`users · tenants · companies · memberships · sessions · auth_tokens ·
invitations · audit_events · outbox · idempotency_keys`

Decisions worth defending:

- **`password_hash` is nullable.** A provider-only identity must not be
  reachable by guessing a blank password.
- **One `auth_tokens` table** for verification, reset, invitation and MFA
  enrolment. They share hashing, expiry and single-use semantics; three
  near-identical tables would drift apart.
- **`companies_one_primary`** — a partial unique index. One primary company per
  tenant is enforced by the database, not by whichever screen sets the flag.
- **`audit_events` has no update path.** The actor comes from the session and
  the detail is redacted before writing.
- **`outbox` with `(topic, idempotency_key)` unique** — the same logical effect
  cannot be enqueued twice.

## 0002 — jobs and schedules

`schedules · jobs · job_runs · missed_occurrences`

- **`schedules.timezone` is stored with the cron.** "Every day at 09:00
  Europe/London" is a different UTC instant in summer and winter; storing only
  UTC silently shifts a customer's schedule twice a year.
- **`jobs_schedule_occurrence_key`** — unique on `(schedule_id, occurrence_at)`.
  This is what makes "exactly one run per occurrence" true under two dispatchers.
  It is also the shape that fixes the prototype's subscription sweep, which
  re-invoiced every active subscription on every click.
- **`fence bigint`** — incremented on each claim. A result carrying an old fence
  is rejected rather than overwriting a newer attempt.
- **`missed_occurrences`** — a run that could not happen is recorded with its
  reason, so "why did this not run" has an answer instead of silence.

## 0003 — CRM

`parties · pipelines · pipeline_stages · leads · deals · deal_stage_history ·
activities`

- **One `parties` table for organisations and people.** A lead, a contact and a
  customer are the same party at different moments. Modelling them separately is
  why converting a lead in the prototype lost its history.
- **Relationships are foreign keys.** The prototype stored a deal's company as
  the *text someone typed*, so renaming an account orphaned its deals and two
  spellings were two companies.
- **`pipeline_stages.outcome`** is explicit (`open`/`won`/`lost`). A report must
  not infer whether a deal was won by matching a stage's name.
- **`merged_into`** keeps a merged party's row so existing links still resolve.
- **`activity_has_one_target`** — a check constraint: an activity is about
  exactly one of a party, a deal or a lead.

## Not yet designed

HR, Travel & Expense, Support, Assets, POS, Pitch Pilot, connectors, guardrails
and compliance all still live in `workspace.tsx`. Their entity maps are in
`docs/implementation/map/` and the operations are rows in `coverage.csv`.

## Rollback

Each migration is additive and applied in a transaction. Rolling the
application back one version is safe against this schema: no column has been
dropped or narrowed, so an older build ignores what it does not know about.
A migration that must narrow a column will need the usual two-step — add, dual
write, backfill, then remove in a later release.
